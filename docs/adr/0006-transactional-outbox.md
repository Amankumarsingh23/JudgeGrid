# ADR 0006: Transactional dispatch intents and expiring relay claims

Accepted for Session 6.

Submission creation must survive a crash between PostgreSQL commit and Redis publication. The existing owner/key transaction now commits the submission, idempotency mapping and one `SUBMISSION_READY` outbox event together. A unique `(submission_id,event_type,intent_generation)` key protects the initial generation without blocking a future intentional generation. No rejudge operation is implemented. Events contain immutable typed references and payload version, never source code, hidden tests or credentials. All languages accepted by the existing API receive an intent; this does not imply runtime support.

A separate explicitly enabled Go relay claims a bounded batch using indexed due/expired candidates, `FOR UPDATE SKIP LOCKED` and a single short update transaction. PostgreSQL assigns an incremented claim generation and fresh UUID token, plus an expiry measured by its clock. No row lock is held across Redis calls. Each batch starts at most 16 concurrent publications, without a queue of preclaimed batches. Bounded publication deadlines and expiring claims are sufficient here; no renewal thread is needed. Finalization checks token, generation, status and unexpired ownership. A stale publisher may still issue XADD, but cannot complete or release another owner's claim.

Redis schema 2 adds a stable `event_id` to the existing thin submission reference. Its `attempt` is the intent generation, not a relay claim generation and not execution ownership. Existing schema-1 development messages remain supported. Redis Stream IDs are physical publication identities: retries can create different Stream IDs with the same logical event ID.

This provides recoverable at-least-once publication, not exactly-once publication or execution. A lost XADD reply is uncertain, even if Redis committed the message. A crash or database failure after XADD leaves the claim recoverable on expiry. The relay republishes the same event identity. Future consumers must commit deduplication and authoritative effects together under worker ownership. Session 6 has no real execution consumer: production consumption remains disabled and the isolated receipt handler refuses real jobs without ACK or state changes. Development receipts separately verify current QUEUED/state-version-zero admission before their unique insert.

Transient/uncertain Redis errors return intents to PENDING with capped exponential equal-jitter backoff. Permanent schema/configuration errors and exhausted retry budgets enter QUARANTINED with safe error codes. Failed database iterations also back off. Operator retry preserves identity and lifetime attempts, starts a new retry budget and cannot release a live claim or published event. Invalid immutable schemas require a compatible deployment, rather than editing history.

New acceptance uses a configured backlog threshold, counting pending, claimed and quarantined intents with a bounded query. A transaction advisory lock serializes new admissions so concurrency cannot overshoot this local database threshold. Idempotent replays bypass admission rejection. This is a simple throughput tradeoff; Redis stream storage and future execution backlog require additional capacity management later. Statistics are bounded and explicitly indicate capped counts. Full observability is deferred.

Historical rows receive no automatic intents. A privileged operator can select one QUEUED submission UUID for idempotent backfill; there is no scan-and-publish migration or public operation. Retention is disabled: published history is immutable and no outbox records or Redis entries are deleted/trimmed. A later explicit retention policy must account for delivery, audit and acknowledgement independently.

Graceful shutdown stops requesting batches and allows an independent bounded drain. If drain expires, contexts cancel and unfinished claims remain recoverable. These publication claims fence only outbox metadata; distributed execution leases, heartbeats and result fencing are Session 7 work. The relay receives no sandbox or Docker daemon authority.
