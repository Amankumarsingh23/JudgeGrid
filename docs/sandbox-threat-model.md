# Sandbox threat model and operating boundary

Untrusted source, stdin, compiler processes and runtime output cross a trusted controller boundary. The API stores owner-scoped submissions and outbox intents in PostgreSQL; an opt-in relay publishes Redis deliveries. Ordinary workers record dispatch receipts. The explicitly enabled host judge agent alone claims database execution authority and invokes Docker. Its recovery scanner also finds durable work without Redis. The private immutable test store and trusted evaluator supply one stdin case and compare output outside containers. Expected outputs and service credentials never enter workloads.

The developer account, controller binaries/configuration, PostgreSQL authority, immutable test store, Docker daemon/runtime, pinned images and Linux kernel are trusted. Docker access is powerful host authority; fixed CLI construction does not reduce the account's daemon permissions. API, worker and relay images have no daemon socket or trusted controller binaries.

Namespaces separate process, mount, IPC, network and cgroup views. Cgroups bound charged memory, task count and CPU allocation rate. Seccomp filters system calls. None creates a separate kernel. Kernel/runtime exploits, side channels and malicious Docker administrators remain outside the demonstrated protection. No user-namespace remapping or VM isolation is claimed.

Both compilation and runtime use UID/GID 10001, dropped capabilities, no-new-privileges, pinned seccomp, network none, read-only root, private namespaces, bounded tmpfs, fixed environment, disabled logging and bounded output capture. Only preparation can write the private artifact volume; runtime mounts it read-only. Fixed paths prevent source-selected mounts or command arguments. Offline pinned images prevent normal execution-time dependency downloads. Retained settings are inspected before start. Missing enforcement, startup or cleanup failures remain infrastructure errors. Exit 137 alone does not establish MLE.

The independent in-container watchdog bounds computation after abrupt controller death. It cannot remove stopped resources. PostgreSQL fencing blocks stale results; a separate host reconciler authorizes exact orphan deletion after expiry, completion or takeover. Go defer handles ordinary cleanup but cannot run after a killed process. Unknown provenance, inconsistent relationships, inventory overflow and unavailable database authority fail closed.

The controlled syscall fixture observes Seccomp mode 2, no-new-privileges, zero effective capabilities and unshare denied with EPERM. That errno cannot attribute the denial specifically to seccomp rather than capability or other kernel checks. CPU quota limits bandwidth, not total CPU time. CPU time and peak memory remain null; controller wall duration remains available.

Named volumes lack a verified aggregate disk quota. Per-file limits and fixed artifacts reduce exposure without proving an aggregate storage ceiling. Future execution storage needs a quota-backed filesystem or bounded compile tmpfs plus a verified size-limited artifact handoff. Reconciliation does not infer ownership from legacy name prefixes or delete host temporary files from labels. Daemon downtime delays cleanup. Docker volume deletion lacks compare-and-delete semantics against a malicious administrator.

See [control/evidence matrix](sandbox-security-controls.md), [operations](sandbox.md), and [ADR 0008](adr/0008-sandbox-provenance-and-reconciliation.md). This development milestone does not prove arbitrary hostile-code production safety.
