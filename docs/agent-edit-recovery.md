# Workspace edit recovery

Migration 0018 adds a child journal to completed research runs. CREATING has no selected version until preparation's transaction commits. A selected pointer marks READY. A stored proposal marks PATCH_PROPOSED. An unexpired pending request is AWAITING_APPROVAL. A database-time lease and attempt row represent APPLYING. A publication receipt marks APPLIED. Denial, cancellation and expiry terminate an approval. The workspace itself expires separately. These states are derived from durable rows rather than duplicated enums.

Every valid proposal is immutable. One workspace admits at most 12 proposal identities. The trusted executor reserves a physical attempt under a new monotonic generation, with a 45-second lease and a 35-second apply deadline. At most three physical attempts can be reserved for one proposal. A failed or interrupted attempt leaves its generation and staged objects durable; its lease becomes reclaimable. Recovery reruns preflight against the expected selected version and rechecks the approval. It reuses staged hashes only after verifying each candidate object.

Blob staging commits independently from selection. A read follows the selected inventory and cannot address an unselected blob. The executor verifies the entire candidate tree, including untouched entries, before a short PostgreSQL transaction inserts the immutable version, changes the pointer using a fenced compare-and-swap, and writes the publication receipt and journal event. Publication and its authoritative journal event commit together. A response lost after commit returns the original receipt on retry. A competing proposal for the old base requires new review. The controller never auto-merges.

The workspace's database transactions hold the authoritative pointer and journal. The external snapshot store provides original bytes at preparation. A snapshot-store error aborts preparation before the first workspace publication. Database errors during staging may leave unselected objects. The policy intentionally includes no automatic object deletion or filesystem cleanup. The backing database operator is within the trust boundary.

Session 19 can consume one selected version through an explicit handoff. Any future materializer must independently enforce path and filesystem safety, and any future validation runner needs its own authority and sandbox policy.
